## 监控入口怎么选

| 页面 | 平台路径 | 用来回答什么问题 |
| --- | --- | --- |
| 运行总览 | `/admin` | 请求质量、任务队列和成本趋势是否异常 |
| 请求明细 | `/admin/logs` | 某次调用用了什么来源、为何失败、如何计费 |
| 登录日志 | `/admin/login-logs` | 指定账号何时登录，是否有异常记录 |
| 邮件记录 | `/admin/email-logs` | 某封验证码或通知邮件是否发送成功 |
| 系统性能 | `/admin/settings/system-performance` | CPU、内存、缓存、队列等是否出现瓶颈 |

先按用户、时间、任务或渠道缩小范围，再读取详情。不要把汇总曲线正常当成某个用户的任务一定成功。

## 处理一条生成失败反馈

1. 收集入口、任务编号、发生时间、模型和错误提示。
2. 在请求明细定位对应调用，区分输入、协议、上游、排队、保存和权限问题。
3. 查看任务最终状态，确认是否已有可恢复作品。
4. 只调整相关配置；能够重新保存时优先恢复原作品。
5. 用同类小任务验证，再回复用户处理结果与是否需要重新操作。

执行器离线要检查服务状态，存储失败要检查资源访问，额度不足要核对账务；不因一个任务失败就重启全部业务。技术排查见 [任务运行稳定性](../backend/task-runtime-stability.mdx)。

## 系统公告与常驻通知

入口：系统公告（`/admin/announcements`）、常驻通知（`/admin/banner-announcements`）。前者用于通知发布和状态管理，后者用于首页顶部持续展示的内容。

1. 写清受影响功能、时间范围和用户需要做的动作。
2. 配置页面提供的状态及有效期，核对展示内容后发布。
3. 用普通账号查看展示位置、阅读效果和到期行为。
4. 发布请求结果不确定时先查已发布记录，再决定是否重试。

更新公告的编写细节见 [更新公告专题](../backend/update-announcements.mdx)。

## 用户反馈

入口：用户反馈（`/admin/feedbacks`）。阅读问题、附件和已有处理记录，按页面支持的回复和状态操作跟进。

先要求补充能定位问题的信息，而不是索取完整密钥。回复中说明已确认原因、已采取措施，以及用户是否需要重试或刷新。

## 存储资源

入口：存储资源（`/admin/resources`）。按用户和资源定位占用，核对实际文件、引用与清理条件。

清理前先确认是否仍被画布、项目、任务或素材引用。删除失败时保留记录继续排查，不能把记录消失当成物理空间已经释放。批量清理先检查范围和可恢复性。

## 日常巡检

查看失败趋势与队列 → 检查模型来源和容量 → 处理未完成反馈及订单异常 → 核对公告有效期 → 观察配置变更后的真实用户效果。保留必要记录，便于下次对照。
