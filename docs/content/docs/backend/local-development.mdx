## 选择入口

完整本地运行使用 `docker compose -f docker-compose.local.yml up -d --build`；它构建 web、backend、Agent，配置准备见根 README。根 `docker-compose.yml` 的 Agent 在 `pi` profile 下，需显式使用 `--profile pi`。生产部署使用 deploy 配合 build 或 server，不能把开发数据目录当作生产目录。

热更新编排 `docker-compose.dev.yml` 仅包含 backend 和 web。先创建它要求的三个宿主机目录：

```bash
mkdir -p .local/project-workbench-debug .local/cache/go-build .local/cache/go-mod
docker compose -f docker-compose.dev.yml config
docker compose -f docker-compose.dev.yml up -d --build
```

数据位于 `.local/project-workbench-debug`，不与其他编排的卷自动共享。该文件有独立项目名，但同机端口仍可能冲突；启动前检查实际映射，按需设置 `CANVAS_BACKEND_HOST_PORT`、`CANVAS_WEB_HOST_PORT`。它没有 Agent 服务；需要完整 Agent 验收时改用 local 编排。

## 宿主机开发

前端使用 Bun 和 `web/bun.lock`，Agent 使用 Node 22.19.0 或更新的兼容版本及 `agent/package-lock.json`。不要给 web 引入 npm/yarn 锁文件。后端使用 Go 1.25，SQLite 路径需要支持 CGO 的 C 编译器。

```bash
cd web
bun install --frozen-lockfile
bun run dev
```

前端代理由 `VITE_API_PROXY_TARGET` 指向后端。后端在另一个终端启动，明确指定隔离数据目录和 CORS：

```bash
cd backend
CANVAS_BACKEND_DATA_DIR=../.local/host-dev CANVAS_CORS_ORIGINS=http://localhost:3000 go run ./cmd/server
```

Agent 构建使用 `cd agent && npm ci --ignore-scripts && npm run build`。启动前准备与 backend 一致的内部连接配置及 harness，配置项以 `.env.example` 和当前编排为准；不要复制生产凭据到开发目录。Agent 本身不需要数据库或公开监听端口。

## 验证范围

优先运行改动模块的测试。示例：前端 `bun test test/<相关文件>`，Agent 在 build 后使用 `node --test dist/test/<相关文件>.test.js`，后端 `go test ./internal/<模块> -run '<相关用例>' -count=1`。Agent 测试引用相邻组件时以真实构建为准。`CGO_ENABLED=0` 只能用于不需要 SQLite 的纯函数测试，不能证明数据库验收通过。

部署脚本的隔离检查是 `python -B -m unittest scripts.test_production_deployment scripts.test_agent_parity_container_commands`。这些测试通过 Docker 替身或配置解析检查合同，不启动完整服务，不能代替真实安装和跨进程验收。依赖 PostgreSQL/Redis 的测试准备见 CONTRIBUTING；测试库必须允许建删临时 schema，不能使用生产 DSN。

首次管理员、注册开关、模型渠道与私网模型地址仍受真实后端策略约束。不要通过默认用户、放开全部私网或跳过归属校验让开发请求通过。下载失败时先判断网络、可用镜像，再检查本机代理；日志和报告不得包含凭据。
