# Agent 会话消息排队设计

状态：待用户确认；尚未修改运行时代码。

## 目标与用户要求

- Agent 会话支持排队消息；用户在 Agent 界面选择默认“插队”或“排队”。
- 前端只呈现选择、消息、状态和操作；业务决策由服务端负责。界面不放调度、事务、恢复等实现说明，也不添加解释产品规则的长文案。
- 沿用当前会话、草稿、权限、模型、技能、预算及画布范围，不创建另一套聊天入口。
- Agent 记忆、上下文压缩、待办管理保持现有设计。

## 已核实的代码基础

- `web/src/components/canvas/canvas-cloud-agent-panel.tsx` 的 `submit` 在运行中直接进入 `interject`，空闲时用当前轮作 parent 创建续轮；目前没有用户消息队列。
- `backend/internal/app/cloud_agent_interjection.go` 允许 queued/running/waiting_approval 接收插话，通过 messageId 去重，并在本轮后续模型调用送达。
- `backend/internal/repository/cloud_agent_conversations.go` 以 conversationId 识别会话，续轮准入要求 parent 为最新终态且 cleanupPending=false；两个设备不能同时分叉创建续轮。
- `backend/internal/app/cloud_agent.go` 已有幂等准入、额度预留及 Prepared 准备路径；队列发出新轮应复用这些校验，不复制模型任务创建链路。
- `backend/internal/app/cloud_agent_runtime.go` 执行 `ask_user` 后记录 user_question 并将本轮标为 completed。自动派发必须另查未回答问题，不能只判断 status。
- `web/src/services/cloud-agent-conversations.ts` 已保存未知提交的原始正文、幂等键、parent 与外部入口保留的草稿；新增发送模式也必须进入该恢复记录。

## 发送语义

“插队”使用现有插话机制：在模型下一处允许接收输入的边界补充当前轮，不强制中断正在执行的模型请求、工具或媒体任务。“排队”是当前轮结束后逐条建立新轮，每条消息独占一轮，不把多条合并成一句输入。

下表是设计者建议的默认行为，均可在实施前调整。

| 会话情况 | 选择插队 | 选择排队 |
| --- | --- | --- |
| 空闲，队列为空，无待回答问题 | 立即创建或继续当前会话 | 进入队列并立即调度为下一轮 |
| 正在执行或等待模型/工具/资源 | 插话进入当前轮 | 追加到队尾 |
| 正在等待审批 | 插话仍可送入当前轮；不能替代审批 | 留在队列，审批解决后继续等待本轮结束 |
| 已有待发项，当前轮刚结束 | 原子创建一个优先续轮，然后恢复原队列 | 加入原队列末尾，不越过先前消息 |
| 当前轮失败、取消、拒绝，或用户停止 | 显式发送可开启恢复轮，原队列继续暂停 | 保存到队尾，队列继续暂停 |
| 存在未回答的 ask_user | 确认控件的回答直接续聊；普通显式消息按下文处理 | 普通消息只排队，不被当成问题回答 |

默认方式初始为“插队”，保持现有用户习惯。用户修改后保存为账号界面设置，跨画布、刷新和设备使用；此设置只决定未来提交，不改变已经收下的消息。它不写入系统提示词、workspace 或 Agent 记忆。

用户点击问题选项、审批通过/拒绝始终走各自明确入口，不受默认发送方式影响。自由回答沿用问题关联：问题栏提供“回答”状态，输入框当前有未回答问题时，显式以插队方式发送才附带 replyToQuestionId；排队消息永不附带。只有带关联并通过服务端校验的输入消除等待问题，不把队列中恰好出现“确认”二字当作同意。

当前轮正常结束、没有未回答问题、没有待审批、清理完成且队列未暂停时，自动派发下一条。新轮再次提出问题时继续等待。用户回答问题后，回答轮正常完成即可恢复派发；异常造成的显式暂停仍需点“继续”。

新建、切换或关闭会话不会将队列搬到另一会话。已获服务端收条的消息在关闭页面后继续按规则执行，另一设备可读取；离线未获收条时只保留待确认请求，不显示“已排队”。

## 前端界面

在发送按钮旁提供一个紧凑的默认方式菜单，常驻只显示当前方式“插队”或“排队”与展开图标；菜单只有这两个选项和当前勾选状态。点击按钮、Enter 与节点发来的提示词使用同一默认方式，快捷键保留现有换行和输入法组合规则。停止按钮保持独立。

有队列时，在输入框上方显示可展开的“待发 3”；展开后每条显示序号、正文摘要和“编辑 / 插队 / 移除”操作。队列暂停时只显示“已暂停”及“继续”。待确认、等待回答、失败等使用简短事实状态；错误显示服务端可操作原因，不显示事务、CAS、幂等键、worker 或调度算法。

编辑在队列项内完成，不覆盖正在输入的草稿；仅未派发项可编辑或移除。点击待发项的“插队”时，由服务端原子改变投递方式：有活跃轮则插话，无活跃轮则优先续轮；失败保留原项，不先删后发。首版不提供拖拽排序、自动合并、定时发送、跨会话迁移或“清空全部”。

外部分镜输入框继续保留 Agent 原草稿，并遵守当前默认方式；成功提示区分“已发送”与“已排队”，不能把入队当执行完成。

颜色、圆角、字体、焦点、浮层和明暗模式沿用当前皮肤；不新增固定色板、固定圆角或解释性横幅。队列列表限定高度并在自身内部滚动，窄面板不撑出横向滚动条。

## 服务端数据与协议

新增独立的用户消息收件表、会话队列控制表和小型账号发送设置。避免把等待消息塞进 run.StateJSON 或浏览器 localStorage，也不恢复已移除的个人长期偏好功能。

消息至少记录 userId、canvasId、conversationId、客户端消息 ID、幂等身份、提交模式、FIFO 序号、revision、请求正文、状态、最终绑定 runId、创建及更新时间。队列控制记录暂停原因、revision、下一个序号及未回答 questionId。账号设置只有 defaultSendMode 与 revision。

等待消息保存发送时的文本、节点 ID、模型选择、权限模式、技能 ID、contextScope、预算及子代理授权请求。实际派发时再按现有链路校验账号权限、模型可用性、技能与最新授权，读取当前画布上下文。后续设置变更不静默改写已入队参数，授权撤销也不能靠旧快照绕过。入队不预留模型费用、不给运行分配资源；实际创建下一轮时才走现有额度预留和调度准入。

首条空会话消息复用现有创建运行入口；它获得 conversationId 后才接受后续队列消息。未知的首条创建必须先核对原幂等请求，不能另造会话。已有会话新增统一发送入口：

- `POST /agent/conversations/:id/messages`：请求携带 mode=interject|queue、原始 CreateAgentRunInput、expectedRunId、可选 replyToQuestionId；服务端决定插入当前轮或保存队列。客户端消息身份来自同一份持久幂等请求。
- `GET /agent/conversations/:id/queue`：返回队列 revision、暂停状态、未回答问题及有序待发项，可按 revision 轻量刷新。
- `PATCH /agent/conversations/:id/queue/:messageId`：携带预期项 revision，更新未派发正文，或提升为插队；操作字段不得混合。
- `DELETE /agent/conversations/:id/queue/:messageId`：携带预期项 revision，取消未派发项，保留内部收条防止未知重试复活。
- `PATCH /agent/conversations/:id/queue`：携带预期控制 revision，执行 pause 或 resume。
- `GET/PATCH /agent/ui-settings`：读取或条件更新 defaultSendMode；它与 systemPrompt/workspace 接口独立。

统一发送收条明确 delivery=interjected|queued|started、messageId、conversationId、queueRevision 与实际 runId（若已派发）；遇到权限、格式等明确失败使用真实 4xx，不返回假成功。相同身份、相同原请求重试返回既有收条；更改正文、模式、问题关联或参数后复用身份返回冲突。当前轮在网络间隙完成时，服务端可在同一会话内转为续轮，但若 expectedRunId 已被另一用户提交推进则返回陈旧会话冲突，不能把用户更正插入陌生新轮。

前端不猜测服务端是否已收下请求。未知提交保存原接口、模式、正文、幂等键和问题关联，恢复后原样查询或重试；不因默认方式切换而修改在途请求。仅收到明确收条后清空对应输入，外部入口仍不清空会话原草稿。切换账号或会话后的旧回执不能更改新作用域状态。

## 调度、并发与恢复

服务端调度器由持久队列驱动，通过现有 worker 生命周期启动，唤醒与有界周期补扫结合；浏览器与 Agent SDK 不负责决定何时发送下一条。

1. 按 userId、conversationId 串行领取，读取最新轮、队列状态、问题与清理状态；同一会话最多一个派发中的消息。
2. 锁内校验最早待发项，选择最新合格 parent，准备既有 CloudAgentAdmission；在一次数据库事务内提交新轮、holding task、额度预留、消息到 runId 的绑定和队列 revision。
3. 进程在准备或提交阶段崩溃后，依据稳定消息身份与已绑定运行恢复；租约过期只重试原身份，不创建第二份运行。多实例竞争、手动续聊和队列派发共用会话串行边界。
4. 原子提升插队与取消同样参与会话串行边界。消息已经派发时，编辑、取消或提升返回冲突并给最新状态；不撤销运行，也不自动转成一次全新发送。
5. 本轮 completed 且无阻塞时推进；failed/cancelled/rejected 或用户停止时暂停队列。停止与派发竞争必须在同一边界决定：要么阻止派发，要么将新轮作为同一次“停止并暂停”的目标，不能漏出一轮继续运行。
6. 明确的模型/技能/权限/额度等准入错误阻塞队首并暂停，消息不丢失、不跳过。临时数据库/网络错误与资源容量不足保留原项、有限指数退避；不越过既有每用户/全局运行配额。
7. 队列修改、消息被接收及派发、问题关联和暂停状态持久记录。队列查询供跨设备刷新；会话目录携带 queueRevision、queuedCount、queuePaused，现有轮 SSE 有更新时通知前端重新取快照。即使没有活跃 SSE 或页面关闭，服务端仍可派发。

提问的 questionId 来自实际 user_question 事件身份，写事件时原子更新队列控制。旧问题按现有事件恢复一次，不能只查末页事件。回答必须引用当前尚未解决的 questionId；问题被新问题替换、已经回答或关联轮不匹配时返回冲突。完整自由文本未调用 ask_user 时不新增猜测性阻塞。

现有直接续聊入口与插话入口仍可供旧调用方使用，但必须参与相同的队列控制和停止/问题关联边界；不能留下绕开串行调度的新旧双入口。未被识别为问题回答的旧续聊请求，在有待回答问题时返回明确冲突。

设计者建议限额：每会话最多 20 条未派发消息，每账号最多 100 条；正文长度复用现有 Agent prompt 上限。两项数量限额纳入现有后台运行策略并热更新，不写死在 UI；降低限额不删现有消息，只阻止新增。队列消息进入既有账号存储配额，提升为运行时同事务替换占用，不能绕过配额或重复计数。无自动过期、无静默丢弃。

## 改动范围

- 后端：独立 queue model/repository/service、数据库迁移、既有准入/终态/ask_user/停止路径接线、服务生命周期、HTTP 与 OpenAPI 合同、service 导出别名、后台运行策略与存储配额。
- 前端：API 与未知请求恢复记录、会话面板调度协调、只负责显示和触发操作的发送模式菜单/队列列表、账号设置缓存与作用域隔离。队列业务规则留在服务端，不塞进 JSX。
- 文档：功能说明、API、数据库与代码地图、待测试清单；实施提交按仓库规范更新版本和 CHANGELOG。
- 不改：Agent 模型推进、记忆/压缩、工具披露、待办算法、媒体任务和付费审批规则。无需升级 Pi SDK 或另引入外部队列依赖。

## 验收重点

- A 运行时入队 B、C：A 结束后 B、C 各执行一次、顺序一致；中间插队 D 只影响当前轮，原队列顺序不变。
- 两种默认方式在按钮、Enter 和分镜节点入口一致；切换默认方式不改变已经排队或未知提交的消息。
- 断网未知 POST、刷新、跨设备、多后端实例争抢与进程重启不重复建轮、不重复预留费用、不串账号或画布。
- 等待审批或 ask_user 时不消费队列；用户明确回答后才续聊，排队中的“确认”不自动回答问题。完成状态也不能跳过问题。
- 当前轮失败、用户停止、权限撤销、模型下线或额度不足时保留并暂停队列；“继续”重验准入，停止与派发竞态不漏运行。
- 编辑/移除/提升与自动派发并发有确定结果；失去 revision 的请求返回新状态，失败不丢原消息，编辑不覆盖输入框草稿。
- 前端只出现必要短标签、内容与操作，沿用皮肤和圆角；真实面板窄屏与键盘可用。定向 React/后端合同和数据库并发验证优先，按用户已允许范围有限测试。

## 建议实施顺序

1. 持久化收件与原子派发，接入准入、暂停、提问和恢复边界。
2. 会话 API、条件编辑/提升、账号默认方式和后台限额。
3. Agent 面板控件、外部分镜入口、草稿及未知提交恢复。
4. 最小充分定向验证、独立复核、文档及版本记录。本地整合与远端推送按用户授权分别处理。
