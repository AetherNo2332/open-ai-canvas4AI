# 工具快照查看、管理与运行总览告警方案

状态：用户已批准实施与提交；实施验收结果见待测试清单。

## 目标与范围

管理员无需等待任务报错、登录容器或读取数据库，就能发现并定位工具快照不一致，查看字段差异、受影响 worker 和任务，并判断恢复结果。以现有后端运行总览和 Agent 调度为入口。

第一版提供查看、比较、重新检测、排空和审计；不在后台编辑 schema、不改写历史任务快照、不触发收费重试、不通过 Docker/SSH 自动升级。

## 已确认的现状

- 运行总览入口：`web/src/pages/admin/admin-route-pages.tsx` 的 `AnalyticsPage`，主体为 `components/analytics-panel.tsx`。
- 已有观测接口：`GET /api/admin/observability/overview`，返回的 `alerts` 是字符串数组；现有页面有“Agent 当前告警”区域。
- worker 在 `agent/src/server.ts` 启动时读取 `TOOL_SCHEMA.json`，在运行任务时由 `runner.ts` 调用 `assertToolSnapshotMatchesSchema`。
- `event-scheduler.ts` 每 15 秒上报一次容量；`AgentRuntimeInstance` 已记录心跳，后台以 45 秒判断在线，但没有工具制品与部署版本信息。
- 任务下发的工具来源是该任务 `state.Canonical.Tools`，由 `piAgentSnapshot` 转成传输快照，并非每次从当前目录重新生成。
- 现有校验比较同名工具的参数 JSON，参数内的 description 变化也会失败。只看 `cloud-agent-tools/v3` 或工具数量不足以判断是否一致。
- 本次 3040 故障同时涉及绘图参数约束变化和媒体参数说明变化，适合作为验收回放样例。

## 方案选择

| 方案 | 收益 | 局限 |
| --- | --- | --- |
| 只从失败日志提取错误并加告警 | 改动最少 | 必须先失败，不能确认修复，也看不到 worker 加载内容 |
| worker 注册制品，后端比较，运行总览展示（推荐） | 可提前发现，可定位，可接入调度 | 需要扩展内部协议和少量持久化 |
| 后台统一发布和切换 schema | 集中控制版本 | schema 与实际二进制能力可能脱节，范围过大 |

选择第二种，按“观测 → 诊断管理 → 调度保护”逐步落地。

## 一、明确三种对象

1. **后端工具目录**：运行中后端二进制真正生成的工具定义全集，包含构建版本、schemaVersion、比较器版本和实例信息。生成逻辑与实际工具目录、制品生成测试共用，不能把磁盘上的 JSON 当成后端执行能力。
2. **worker 制品快照**：该 worker 进程实际读入内存的工具定义及其构建版本、协议版本、启动标识、加载时间。不能用磁盘当前内容冒充进程已经加载的内容。
3. **任务冻结快照**：任务创建时冻结的实际工具集合，关联 runId、版本及来源。权限、视觉、技能等条件会裁剪集合；子集不是异常。

快照不可变，工具正文去重保存，任务只关联快照记录和已有运行数据；不额外复制用户提示词、密钥、工具实参或结果。快照 ID 是后端分配的标识，不以新增反复全量哈希作为主要检测办法。

## 二、注册、心跳与比较

- worker 启动后先注册实际已加载的完整制品；后端校验名称唯一、工具结构、大小和嵌套深度，并返回快照 ID 与检测结果。
- 使用进程级 `instanceId + bootId` 关联注册、容量心跳和领取任务。现有 slot workerId 与容量上报 owner 不完全相同，不能简单按字符串相等关联。
- 复用现有 15 秒心跳，只携带快照 ID、加载代次和检测状态；工具正文仅在首次注册或进程实际重新加载时发送。
- 后端重启后重新校验；注册记录丢失时要求重新注册，不能沿用“已一致”。磁盘文件改动但进程未重载时显示“磁盘与已加载版本不同”，不声称生效。
- 全目录漂移用于诊断；具体任务按其冻结工具子集，检查同名参数是否与实际 worker、当前承接后端一致。
- 差异给出工具名、JSON Pointer、变化类型、旧值和新值，限制单项和总响应大小。包含新增/缺失工具、必填项、类型、枚举、约束及说明文字变化。
- 第一版继续采用当前严格比较语义，说明文字变化也明确标为“当前 worker 校验器会拒绝”，不能一边展示为兼容、一边运行失败。
- 若后续将说明变化降为非阻断，必须同时更新 Go/Node 的共享比较规则并用同一组测试样例验证；不能在此版本顺带放宽。
- 保留现有明确的兼容例外，并将比较器版本及实际适用规则记录到结果中。

## 三、运行总览展示

在运行总览靠前位置增加独立的“工具快照状态”区域，放在历史趋势之前；系统当前健康不受日期、用户、渠道和模型筛选影响。

推荐文案：

> 工具快照不一致：1 个在线 worker 与当前后端存在差异，涉及 canvas_edit_drawing、generate_media。2 个待运行任务受影响。最近检测：刚刚。［查看差异］

状态分开显示“当前差异”和“执行影响”：

| 状态 | 展示与含义 |
| --- | --- |
| 一致 | 绿色：已注册、在线且完成当前版本检测 |
| 存在漂移，尚无受影响任务 | 黄色：显示差异及潜在影响，不能计为完全健康 |
| 运行被阻断 | 红色：已有任务无兼容执行组合，或注册制品损坏/缺失、协议不受支持 |
| 未知/检测失败 | 灰色或黄色：旧 worker 未上报、接口异常或检测未完成，不显示绿色 |
| 离线 | 单独标记，复用现有 45 秒阈值；不继续算作在线漂移 worker |
| 已恢复 | 当前告警消除，事件时间线保留原异常、恢复时间及处理记录 |

- 提供异常 worker 数、受影响工具数、等待任务数和最近检测时间。
- 同一个异常按来源和快照组合合并，保留首次发现、最近发现和恢复时间，避免每次心跳新建告警。
- 不提供“已读即健康”；如做确认，只改变确认状态，异常本身仍保留。
- 页面可见时约每 15 秒刷新当前状态，后台标签页暂停，切回立即刷新；提供手动刷新。
- 当前风险告警与历史失败分开；历史任务仍保留旧快照不代表故障再次发生。

## 四、查看与管理交互

从告警进入“工具快照”详情，支持通过稳定 URL 定位当前筛选和所选快照，避免只存在于一次性弹窗状态。

### 快照列表

展示来源（后端/worker/任务）、快照 ID、应用版本与提交、schemaVersion、工具数量、加载/创建时间、在线引用数量、关联任务及当前检测结果。支持按来源、版本、状态、工具名筛选。

### 快照详情与比较

工具列表可搜索，右侧展示参数结构；默认只看差异，可切换完整定义。提供“后端 ↔ worker”“任务 ↔ worker”“任务 ↔ 当前后端”三种比较，并展示检测时间与比较器版本。

任务详情显示冻结版本、承接 worker 和不兼容原因；仅列出有管理员权限访问的关联任务，不直接展开用户内容。

### 第一版管理操作

- **重新检测**：基于进程上报内容重新比较，不隐含热加载文件或重启 worker。
- **导出诊断包**：仅导出工具定义、版本、差异和状态，经过字段白名单；不含内部 token、用户输入、环境变量或敏感主机路径。
- **排空 worker**：停止领取新任务，现有兼容任务按原租约继续；后台显示未结束任务数。
- **解除手工排空**：需完成最新检测；自动判定不兼容的限制不能靠此按钮绕过。
- 所有写操作记录管理员、原因、目标、前后状态和结果，并带 revision 防止并发覆盖。

暂不提供“强制忽略校验”“覆盖历史快照”“删除仍被引用的快照”“一键重跑失败任务”。历史清理需另有保留期与引用保护设计，第一版不自动删除。

## 五、任务调度保护

先上线可靠观测，再接入调度，避免 UI 状态与执行行为脱节。

- 领取任务前，后端验证 worker 注册身份及当前加载代次，并在授予租约前检查三方所需工具是否兼容。
- 有兼容 worker 时交给兼容实例；不因一个 worker 漂移而停掉全部实例，也不误伤它仍可执行的历史任务。
- 无兼容组合时，任务保持 queued，使用 `waiting_resource` 和明确的 `tool_snapshot` 原因展示等待；不领取后立刻失败、不消耗模型请求、不重复计重试。
- 匹配应发生在租约事务边界内，并避免队首不兼容任务阻塞后续兼容任务；按冻结快照和制品组合缓存比较结果，加载代次或比较器变化时失效。
- 正在运行的任务不被热改写或自动重放。仍保留运行前的本地校验，作为最终防线。
- 后端本身无法执行的历史快照也不能仅因 worker 匹配就放行；明确提示需要兼容后端或人工处理。
- 后端为多副本时，目录必须记录到实际后端实例；滚动升级中的两个版本不能互相覆盖成“集群唯一当前版本”。
- 旧 worker 未注册时显示 unknown；先观测并升级全部 worker，再启用领取门禁。强制门禁启用后未注册实例不得领取，防止静默绕过。

## 六、数据与接口建议

优先复用 `AgentRuntimeInstance`、容量心跳、管理员鉴权与现有告警入口，不另造完整监控平台。

建议新增不可变工具快照记录、实例与快照关联、结构化快照异常记录；任务关联冻结快照 ID。迁移先加可空字段，对旧任务按需提取，避免启动时扫描全部历史运行。历史缺失必须显示 unavailable，不伪装成当前版本。

建议接口（路径是设计提案）：

- `POST /internal-agent/tool-snapshots/register`：注册已加载制品；仅用现有内部认证，不作为管理员接口。
- 现有 `POST /internal-agent/capacity` 增加 instanceId、bootId、snapshotId 和加载代次。
- `GET /api/admin/agent/tool-snapshots`：列表与筛选。
- `GET /api/admin/agent/tool-snapshots/:id`：单份详情和引用概况。
- `GET /api/admin/agent/tool-snapshots/compare?left=...&right=...`：字段差异。
- `GET /api/admin/agent/tool-snapshot-health`：不受历史分析筛选影响的当前状态。
- `POST /api/admin/agent/tool-snapshot-checks`：受限频率的重新检测。
- worker 排空/解除排空接口，复用管理配置的 revision 与审计惯例。

现有 `alerts: string[]` 可在过渡期保留，增加有 code、severity、source、firstSeenAt、lastSeenAt、resolvedAt、受影响对象和详情链接的结构化异常；业务逻辑不再解析英文错误字符串。

## 七、落地顺序

1. **提前告警**：统一生产目录与制品生成入口；注册与心跳；持久化差异；当前健康接口；运行总览顶部告警。完成后无需创建任务即可发现本次 3040 问题。
2. **查看与管理**：列表、字段比较、关联 worker/任务、诊断导出、重新检测、排空和审计。所有操作真实区分“已请求”和“已生效”。
3. **领取保护与部署约束**：兼容实例调度、无兼容实例等待、并发/租约验证；worker 镜像内包含配套制品，正式编排避免挂载会随源码变化的活动 schema。开发挂载明确标识，不自动热更新运行中任务。

主要代码落点：

- worker：`server.ts`、`runtime-config.ts`、`bridge.ts`、`event-scheduler.ts`、`tool-disclosure.ts`。
- 后端：工具目录与制品生成、`agent_scheduler_policy.go`、`internal_agent.go`、实例 model/repository、管理观测接口和调度领取边界。新增聚焦的快照比较与管理文件，避免继续扩大已有大文件。
- 前端：`analytics-panel.tsx` 接入独立当前状态；新增快照列表与详情组件；服务请求使用现有 `http` 入口。
- 文档：同步数据库、HTTP API、部署说明及待测试清单。

## 八、验收标准

- 无任务时也能发现旧后端与新版 worker 制品不一致，完成注册后下一次总览刷新即可看见；运行中异常最迟在一次心跳加刷新周期内可见。
- 精确回放本次两个工具差异，展示绘图 record.id 约束与生成提示词说明变化；保留严格校验行为。
- 参数对象键序变化不告警；权限/能力造成的工具子集不告警；缺工具、同名参数变化、损坏制品明确报出。
- 未上报、心跳超时、快照读取失败、服务端检测失败不能显示为一致。
- worker 启动后磁盘 schema 改变，不会被误显示成内存已更新。
- 多 worker 中仅一个漂移时，兼容任务仍正常领取；无兼容实例的任务等待且不产生模型请求。
- 覆盖旧任务恢复、滚动升级、多后端版本、worker 重启标识变化和比较规则升级。
- 日期/用户/渠道筛选不会隐藏当前系统异常；修复后当前告警自动解除，历史事件仍可追溯。
- 检测刷新、排空和解除排空有权限与并发测试；诊断包无 token、环境变量或用户内容。
- UI 检查包含明暗模式、皮肤 token、窄屏、键盘操作、长差异和请求失败状态。

## 实施边界

用户已要求完成并提交全部方案。实现覆盖提前告警、查看与管理和领取保护；代码提交不等同于部署验收，不自动更新运行中的服务或重试用户任务。
