# Pi 本地工具参数拒绝导致批次 403：调查与验收

## 原因和修复

原失败运行 `agce72e71e7f644899e3135bcc4a1a8798` 的第一步 `ask_user` 将 `options` 数组发成字符串。Go 已登记工具批次，预检保存 `schema_error / type_mismatch / options`；Pi SDK 0.87.1 在调用 execute 之前校验参数并直接返回 `toolResult(isError=true)`，因此没有向 Go 请求工具推进。

原检查点只保存 Pi 消息，没有结算该预检拒绝调用：`callIndex=0`、批次还有 1 个调用。下一步模型纠正参数后，新的批次因旧调用未完成被 Go 拒绝，产生用户看到的 403。此处是执行合同拒绝，与账号权限和 CORS 无关。

修复在工具结果检查点事务内检查当前批次、调用顺序、callId、工具名和服务端持久化预检。只有预检拒绝且 Pi 返回错误的当前调用，才复用 Go 的错误回执、事件和纠错计数逻辑结算；有效工具不能被客户端错误结果跳过，也不接受伪造成功或业务副作用。重放不重复结算。Pi SDK 保持不变。

## 验证

- 新回归先失败（无效 options 的 callIndex 保持 0），修复后通过；覆盖有效参数、错误 callId、错误工具名不能跳过、错误回执持久化、检查点重放、纠正后的批次准入。
- Go Pi/工具/提问/准入相关 app 测试通过（29.57 秒），repository/handler 相关测试通过；Agent 全套 127/127 通过。
- 用户明确授权后，使用已有真实文本渠道 `qwen3.8-27b` 测试，而非可控模型桩。7 轮、15 次模型调用全部完成：画布读取和 ask_user、同一会话续聊、审批通过、一次新增脚本文本节点、SSE 续传、4 个独立会话并发。
- 真实 LLM 确实首次发出了字符串 options；持久化 Pi 消息中存在 `Validation failed ... options: must be array`。随后纠正为数组并完成 ask_user，没有批次 403。数据库核对所有 7 轮工具均已结算，提问和续聊属于同一 Pi conversation。
- SSE 首次返回 40 个事件，从游标 79 重连返回其后 19 个，顺序一致。
- 补充 16 个真实 LLM 会话（4 个画布）全部完成，产生 32 次成功模型调用，已开始模型任务的时间窗重叠峰值为 16。逐轮确认已解析模型为 qwen3.8-27b；没有修改渠道限制。该指标来自任务开始/结束时间，不声称测量了上游内部 GPU 执行并发。
- 合计 23 轮真实会话、47 次模型调用通过。审批新增的节点类型为 text、正文 227 字且非空，标题正确；原画布未写入。

运行详细记录和请求 ID 保存在本地私有 `.local/real-llm-acceptance.json`、`.local/real-llm-16-acceptance.json`。16 路辅助验收最初错误地检查了为空的 task.model 字段，业务已经全部完成；改用执行记录的已解析模型复核后通过，没有重复发起模型请求。测试脚本 `scripts/verify-agent-real-llm.py` 必须显式指定渠道和模型，可用 `--parallel-sessions 16` 复验，会调用真实渠道，不能作为无费用默认测试。
